SHL Conversational Assessment Recommender

Approach Document — AI Intern Take-Home Assignment | Shivam Mishra

1. Design Overview

The system is a stateless conversational agent that guides recruiters from vague hiring intents to a grounded shortlist of SHL Individual Test Solutions. It combines semantic retrieval (FAISS + SentenceTransformers) with LLM-driven dialogue (Groq/Gemini) to handle four core behaviors: clarify, recommend, refine, and compare.

User → FastAPI (POST /chat) → Agent │ ┌ Extract search queries (regex + NLP) │ Retrieve top-20 catalog items (FAISS + keyword boost) │ Build system prompt with catalog context └ Call LLM (Groq → Gemini fallback) │ ┌ Parse JSON response └ Validate recommendations against catalog whitelist │ ChatResponse (reply + recommendations + end_of_conversation)

Key design decision: The API is fully stateless — every POST /chat carries the complete conversation history. This simplifies deployment (no session storage) and matches the evaluator's replay model.

2. Data Pipeline & Catalog

  • Scraping: Custom BeautifulSoup scraper fetches all 374 Individual Test Solutions from SHL's paginated catalog (?type=1). Extracts name, URL, test type codes (A/B/C/D/E/K/P/S), remote testing, and adaptive/IRT flags.
  • Enrichment: Concurrent detail-page fetcher adds descriptions (up to 600 chars), durations, and job levels using multiple CSS selector fallbacks for robustness.
  • Resilience: HTTP session with retry adapter (3 retries, exponential backoff on 429/5xx), URL deduplication, and consecutive-error tolerance.
  • Output: shl_catalog.json — 374 items, all with descriptions (9 items received generated fallback descriptions from names/types).

3. Retrieval Setup

Semantic Search

  • Model: all-MiniLM-L6-v2 (384-dim, fast, good for short text)
  • Index: FAISS IndexFlatIP on normalized embeddings (cosine similarity)
  • Pre-built at Docker build time for fast cold starts
  • Thread-safe lazy loading with double-checked locking

Keyword Boosting

  • Retrieve 3×top_k candidates, then re-rank
  • +0.15 for name token match, +0.05 for description match
  • +0.1 for test-type keyword alignment (e.g., "java" → K type)
  • Bonus capped at 0.4 to prevent over-weighting

Multi-query search: The agent extracts up to 5 queries per turn (combined user text, latest message, detected tech skills, roles, and type-specific queries), runs each through FAISS, and merges by max score. This captures both broad intent and specific keywords.

4. Prompt Design

  • System prompt defines four behaviors (clarify/recommend/refine/compare), strict guardrails (SHL-only scope, no invented URLs, prompt injection refusal), and matching guidelines per role type (technical → K+A, managerial → P+C, customer-facing → S+P+B).
  • Dynamic catalog context: The top 20 retrieved items are injected into the system prompt with name, URL, type codes, descriptions, remote/adaptive flags. This grounds the LLM's responses in real catalog data.
  • Response format: LLM outputs strict JSON (reply, recommendations, end_of_conversation). Three-tier JSON extraction handles clean output, markdown fences, and noisy responses.
  • Post-validation: Every recommendation URL is checked against the catalog whitelist. Names are canonicalized from the catalog. Duplicates removed. Max 10 items.

5. Agent Behavior Design

  • Clarify: Agent asks 1-2 focused questions for vague queries ("I need an assessment") before recommending. System prompt says: "Do NOT over-ask — if the user gives a role + skills, that is enough."
  • Recommend: Once a role OR skill area is identified, provide 1-10 assessments with name, URL, and primary test type code. Aim for 2-3 turns total.
  • Refine: When constraints change ("also add personality tests"), update the shortlist incrementally. The full conversation history in each request makes this natural — the LLM sees the prior recommendations and user's edit.
  • Compare: For comparison queries, the system prompt mandates using only the injected catalog data, not the model's prior knowledge.
  • Scope enforcement: Off-topic requests (legal, salary, general hiring advice) are politely refused. Prompt injection attempts are declined.

6. LLM Provider Strategy

  • Primary: Groq (Llama 3.3-70B) — fast inference, free tier, good JSON adherence
  • Fallback: Google Gemini 2.5 Flash — used when Groq fails or is region-blocked
  • Both providers: temperature 0.2, 2048 max tokens, 3-attempt retry with exponential backoff on rate limits
  • Non-rate-limit errors return None and fall through to the next provider instead of crashing

7. Evaluation Method

Automated Tests (28 unit tests)

  • Catalog integrity: all 374 items have valid URLs, descriptions, test types
  • Search query extraction: tech keywords, roles, multi-turn, edge cases
  • JSON extraction: clean, fenced, noisy, and fallback cases
  • Keyword scoring: match, no-match, cap behavior
  • Trace validation: schema + expected assessments exist in catalog

Behavior Probes (6 probes)

  • Refuses off-topic (legal, salary questions)
  • Clarifies vague queries (no recs on "I need an assessment")
  • Recommends with sufficient context
  • Handles multi-turn refinement
  • Rejects prompt injection attempts

Conversation traces: 10 realistic test scenarios (Java developer, senior manager, customer service, graduate hire, data engineer, sales, .NET developer, vague query, refinement, comparison) with labeled expected assessment shortlists. Recall@10 computed per trace and averaged.

8. What Didn't Work & How I Improved

  • Pure semantic search alone missed obvious keyword matches (e.g., "Java 8" for a Java query). Adding keyword boosting with type-aware re-ranking improved Recall@10 significantly.
  • Single search query per turn was too narrow for multi-faceted requests ("Java developer with leadership skills"). Multi-query extraction (tech + role + type patterns) with max-score merging captured more relevant results.
  • Gemini-only deployment failed in some regions due to API restrictions. Adding Groq as primary with automatic fallback resolved availability issues.
  • Empty catalog descriptions (9 items) degraded embedding quality for those items. Generated meaningful fallback descriptions from names and test types.
  • LLM sometimes invented URLs or hallucinated assessment names. Post-validation against the catalog whitelist eliminated this — only verified URLs are returned.
  • Over-asking (5+ turns) before recommending frustrated the simulated user. Prompt tuning ("aim for 2-3 turns", "role + skills is enough") reduced unnecessary clarification rounds.
